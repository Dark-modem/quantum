# آزمایشگاه ماتریکس — سنجش کیفیت شبکه و مصرف ترافیک

> سند به زبان فارسی | نسخه ۱ | مسیر: `docs/MATRIX-AGENT-LAB.md`
> کد آزمایشگاه: `tests/matrix-agent-lab/`

این سند توضیح می‌دهد که آزمایشگاه «ماتریکس» چگونه کار می‌کند، چه چیزی را واقعاً اندازه می‌گیرد، چه چیزی را **اندازه نمی‌گیرد**، و معیارهای پذیرش برای اولین استقرار Matrix کدام‌اند.

---

## ۱. هدف

قبل از استقرار واقعی تونل Matrix (هستهٔ tinc که `matrix.sh` نصب می‌کند)، باید در محیطی ایزوله و تکرارپذیر ثابت کنیم:

1. مقاومت در برابر DPI و فایروال (در حد واقعیت‌های قابل‌اندازه‌گیری)
2. تأخیر و جیتر پایدار و اتلاف بستهٔ کمینه
3. توان عبوری
4. مصرف منابع (CPU/RAM)
5. **حداقل ترافیک RX قابل‌حساب‌کاری ایرانی** — معیار کلیدی

ترجیح ما اتصال **پایدار ۸ مگابیت** است، نه اتصال سریع‌تر اما ناپایدار. تمام اولویت‌بندی سناریوها و معیارهای پذیرش از همین اصل پیروی می‌کند.

## ۲. ایمنی — چرا این آزمایشگاه خطرناک نیست

| تضمین | سازوکار |
|---|---|
| هرگز قوانین سراسری iptables/nftables پاک نمی‌شود | قبل و بعد از هر اجرا از فایروالِ root هش و dump کامل گرفته می‌شود؛ اگر تفاوتِ dump شامل نام اشیای آزمایشگاه (`qmx…`) باشد «آلارم سخت» می‌دهد. هر تغییر خارجی (مثلاً fail2ban میزبان) فقط با تعداد خطوط گزارش می‌شود |
| حسابداری فایروال فقط داخل namespace آزمایشگاه | زنجیره‌های mangle با نام یکتا فقط در ns ایران ساخته و هنگام teardown دقیقاً همان‌ها حذف می‌شوند |
| shaping فقط روی veth آزمایشگاه | `tc netem` فقط روی egress تونل داخل namespaceها اعمال می‌شود؛ هرگز روی کارت شبکهٔ فیزیکی |
| نام‌گذاری یکتا | هر شیء با پیشوند `qmx<RUNID>_` ساخته می‌شود؛ `labctl clean` فقط همان الگو را حذف می‌کند |
| اجرای اجباری در محیط یک‌بارمصرف | lab روی ماشینی که قابل تشخیص VM/کانتینر/WSL نباشد اجرا نمی‌شود مگر `LAB_FORCE=1` |
| بدون تماس با سرور واقعی | کل توپولوژی (کلاینت، ایران، خارج) سه namespace روی یک ماشین‌اند؛ `production_contact: none` در گزارش ثبت می‌شود |

بررسی خودکار اسکریپت‌ها: `sudo ./bin/labctl audit` الگوهای ممنوعه (`iptables -F` سراسری، `nft flush ruleset` و…) را در سورس خود lab جست‌وجو می‌کند.

## ۳. معماری آزمایشگاه

```
ns کلاینت            ns ایران (سمت قابل‌حساب‌کاری)        ns خارج
  wan0 ── veth ── wan0 ─┤ ├─ tlink ── veth ── tlink
10.100.0.2      10.100.0.1   10.200.0.1        10.200.0.2
                             matrix (tun tinc)  matrix (tun tinc)
                             172.16.99.1        172.16.99.2 + سرویس HTTP
```

* **wan0** نمایندهٔ نیمهٔ «سمت کلاینت» کارت شبکهٔ فیزیکی ایران است.
* **tlink** فقط ترافیک کپسوله‌شدهٔ Matrix (پورت ۲۰۹۷ TCP+UDP) را عبور می‌دهد — جداسازی ترافیک تونل «از روی ساختار» تضمین‌شده است.
* **matrix** اینترفیس tun واقعی tinc است (tinc نام اینترفیس را از netname می‌گیرد — دقیقاً مثل سرور واقعی).
* سناریوی آسیب (netem) روی خروجی tlink در هر دو جهت اعمال می‌شود؛ ترافیک کلاینت شکل نمی‌گیرد.
* موتور در سه حالت: `real` (دو نمونهٔ واقعی tincd با کانفیگ موقت — `/etc/tinc` دست نمی‌خورد)، `calibration` (فوروارد ساده برای صحه‌گذاری روی ریاضیاتِ حسابداری — این تونل نیست!)، `external` (اتصال Matrix Agent MVP آینده از طریق `ENGINE_CMD`).

نقشهٔ شمارشگرها (هر بسته دقیقاً یک‌بار شمرده می‌شود — قوانین iptables داخل ns ایران با کامنت یکتا):

| کلید | محل | معنا |
|---|---|---|
| `client_payload_rx` | PREROUTING -i wan0 | بارهٔ کاربر ورودی به ایران |
| `client_payload_tx` | FORWARD -o wan0 | بارهٔ کاربر خروجی به کلاینت |
| `transport_wire_rx/tx` | tlink | بایت‌های سیم تونل (کپسوله) |
| `matrix_iface_rx/tx` | FORWARD ±i matrix | بایت‌های decapsulate/کپسوله در اینترفیس ماتریکس |

## ۴. حسابداری ترافیک — معیار کلیدی

پارامتر `BILLING_MODEL` **قابل تنظیم است و از نام اینترفیس حدس زده نمی‌شود**:

* `interface-counter` (پیاده‌سازی‌شده): دلتای بایت RX کارت فیزیکی در بازهٔ تست. در lab، جمع `wan0 + tlink` سمت ایران، چون در واقعیت هر دو روی یک NIC.Provider می‌روند.
* `provider-api` / `quota-panel`: اگر صورت‌حساب Provider از API/پنل بیاید، lab عمداً هر نسبت را `UNKNOWN` گزارش می‌کند — حدس زدن معناشناسی صورت‌حساب ممنوع است.

### تست‌های کنترل‌شده

انتقال دقیقاً ۱۰۰ مگابایت (قابل تنظیم) در هر جهت با `payload_client/payload_server`؛ زیرپنجره‌ها برای سنجش پایداری.

### نسبت‌های مشتق‌شده — صورت و مخرج هم‌جهت

```
تقویت RX قابل‌حساب‌کاری (دانلود) = ΔRX فیزیکی ایران / بایت دانلود کلاینت
تقویت RX قابل‌حساب‌کاری (آپلود)  = ΔRX فیزیکی ایران / بایت آپلود کلاینت
سربار ترنسپورت (دانلود)         = transport_wire_rx / بایت دانلود
سربار ترنسپورت (آپلود)          = transport_wire_tx / بایت آپلود
```

اگر هر طرف اندازه‌گیری نشود، خروجی صریحاً `UNKNOWN` است — هیچ عددی «حدسی» گزارش نمی‌شود.

### صحه‌گذاری روش (calibration)

اجرای `calibration` باید تقویت ≈ ۱٫۰۰ بدهد. در اجرای صحه‌گذاری انجام‌شده: بار ۱۵٫۸۱۴٬۴۸۹ بایت، RX قابل‌حساب ۱۵٬۸۳۶٬۹۰۱ → **۱٫۰۰۱۴** ✓ روش سالم است.

## ۵. سناریوهای شبکه

| سناریو | پروفایل netem | کاربرد |
|---|---|---|
| `clean` | بدون آسیب | کف سالم veth |
| `lossy2` | delay 20ms + loss 2% | اتلاف بسته و بازیابی |
| `jitter30` | delay 15ms±30ms | جیتر |
| `congested8m` | delay 40ms±5ms + rate 8mbit + loss 0.5% | **سناریوی مرجع پذیرش (۸ مگاپایدار)** |
| `satellite` | delay 300ms±20ms + loss 1% | بدترین حالت مسیر |

تست‌های سرعت بزرگ «هر دقیقه» اجرا نمی‌شوند؛ انتقال کنترل‌شده فقط در همین سناریوها انجام می‌شود.

## ۶. دوازده تست

T01 برپایی و اتصال (زمان تا اولین پینگ داخل تونل) · T02 تأخیر (پنجرهٔ ۶۰ ثانیه، `ping -i 0.2`) · T03 جیتر (میانگین قدرمطلق اختلاف پشت‌سرهم — RFC3550) · T04 اتلاف بسته (ICMP + پروب UDP مستقل) · T05 توان عبوری (زیرپنجره‌ها + ضریب تغییرات) · T06 بازیابی بعد از قطعی ۸ ثانیه‌ای لینک · T07 CPU (نمونه‌گیری ثانیه‌ای tincd) · T08 RAM (اوج VmRSS) · T09 RX/TX اینترفیس‌ها · T10 ترافیک ترنسپورت · T11 بارهٔ اپلیکیشن · T12 تقویت RX.

## ۷. مانیتور سلامت آینده Quantum (پنجرهٔ ۶۰ ثانیه)

`health/evaluate_window.py` با `health/thresholds.json` رفتار مانیتور آینده را شبیه‌سازی می‌کند:

* پنجره‌های لغزان ۶۰ ثانیه‌ای فقط از پروب‌های ارزان (ICMP/UDP هر ۰٫۵ ثانیه) — **بدون تست سرعت**.
* شکست پنجره: loss > ۵٪ یا p95 > ۲۵۰ms یا میانگین > ۱۵۰ms یا جیتر > ۵۰ms.
* **هیسترزیس نامتقارن ضدلرزش**: دو پنجرهٔ متوالی بد → degraded؛ سه پنجرهٔ متوالی خوب → healthy. نوسان موقت هیچ‌وقت وضعیت را عوض نمی‌کند (در اجرای lab: ۰ تغییر وضعیت روی مسیر پایدار).
* معیارهای موردانتظار هر سناریو به‌صورت overlay در همان فایل آمده است.

## ۸. DPI — چه چیزی واقعاً اندازه‌گیری می‌شود

اصل صداقت: **اتصال موفق به‌خودی‌خود یعنی «مقاومت در برابر DPI» نیست.**

| بخش | روش lab | خروجی |
|---|---|---|
| شناسایی پروتکل | کپچر سیم تونل + جست‌وجوی نشانگرهای متنی | واقعیت بایت‌های سیم در بازهٔ کپچر — **کپچر پنجرهٔ steady-state را پوشش می‌دهد؛ دست‌دادن اولیه قبل از کپچر است و در این نسخه ضبط نشد (محدودیت مستند)** |
| الگوی ترافیک | هیستوگرام اندازه بسته و فواصل زمانی در حالت idle | اندازه‌گیری‌شده در اجرای مرجع: میانگین ~۱۱۱ بایت، میانگین فاصله ~۳۰۰ms — الگوی قابل‌انگشت‌نگاری |
| پروب فعال | اتصال TCP خام، بایت‌های آشغال، HTTP GET، ClientHello، خط ID جعلی tinc، بستهٔ UDP | نتیجهٔ واقعی اجرا: اتصال TCP پذیرفته می‌شود اما به هیچ پروب سالم یا خراب پاسخی نمی‌دهد (سکوت کامل)؛ UDP بی‌پاسخ |
| انگشت TLS | tinc سرویس TLS نیست | `not_applicable` — مقاومت انگشت TLS فقط اگر ترنسپورت TLS پیچیده شود موضوعیت دارد |
| رفتار ریست | از نتایج پروب‌ها | RST صادر نمی‌شود؛ اتصال‌های آشغال بی‌پاسخ رها می‌شوند |
| دسترس‌پذیری روی شبکهٔ تست مالک | **اجرا نمی‌شود** (`NOT_RUN`) — فقط خودِ مالک با شبکهٔ تأییدشده | بدون این، هیچ ادعایی دربارهٔ DPI واقعی ایران مجاز نیست |

هر آنچه خارج از این فهرست است در گزارش `UNKNOWN` می‌ماند.

## ۱۰. معیارهای پذیرش اولین استقرار Matrix

وضعیت هر معیار یکی از `PASS / FAIL / UNKNOWN` است؛ `UNKNOWN` یعنی هنوز اجازهٔ استقرار بر اساس آن معیار نیست. اعداد ستون «نتیجهٔ اجرا» از اجرای مرجع `run-b6c83d54` (senario congested8m، موتور real، بار ۱۰۰MiB دوطرفه) و اجرای صحت‌سنجی `run-f8de5b68` است.

| # | معیار | آستانه | نتیجهٔ اجرا | وضعیت |
|---|---|---|---|---|
| AC1 | برپایی تونل روی مسیر ۸Mbps ناپایدار | برقراری ≤ ۳۰s | ۳٫۹s | ✅ PASS |
| AC2 | تأخیر در پنجره‌های ۶۰s | p95 ≤ ۲۵۰ms، جیتر ≤ ۳۰ms | p95=۸۸٫۳ms، جیتر=۱۶٫۲ms | ✅ PASS |
| AC3 | اتلاف بسته | ≤ ۲٪ روی congested8m | ۰٫۵٪ پروب UDP | ✅ PASS |
| AC4 | **پایداری ۸ مگابیت** | ≥ ۶٫۸Mbps؛ CV ≤ ۲۰٪ | میانگین ۷٫۰۶Mbps، **CV=۰٫۱۱٪** | ✅ PASS |
| AC5 | بازیابی | اتصال مجدد ≤ ۳۰s؛ انتقال ادامه یابد | ۵٫۱۷s، انتقال کامل | ✅ PASS |
| AC6 | منابع | CPU ≤ ۱۵٪ یک هسته؛ RSS ≤ ۶۴MiB | CPU=۱۱٫۳٪، RSS=۶٫۲۵MiB | ✅ PASS |
| AC7 | **تقویت RX قابل‌حساب‌کاری** | ≤ ۱٫۱۰ | **دانلود ۱٫۱۲۴۶ / آپلود ۱٫۱۰۱۵**؛ سربار ترنسپورت ۱٫۰۷۵ / ۱٫۰۸۰ | ⚠️ دانلود بالاتر از هدف |
| AC8 | DPI | واقعیت‌های سیم + پروب فعال مستند؛ بدون ادعای مقاومت | مستند شد؛ دسترس‌پذیری شبکهٔ مالک = NOT_RUN | 📋 مستند |
| AC9 | ایمنی lab | فایروال root بدون تغییر lab-منشأ؛ صفر شیء یتیم | تأیید شد (تغییرات خارجی fail2ban جدا گزارش شد) | ✅ PASS |
| AC10 | صحت‌سنجی روش | تقویت calibration ≈ ۱٫۰۰ ± ۵٪ | **۱٫۰۰۱۴** | ✅ PASS |

### تحلیل AC7 — مهم‌ترین یافته برای تصمیم استقرار

تقویت دانلود ۱٫۱۲ یعنی برای هر ۱۰۰ مگابایتِ دانلودِ کاربر، حدود ۱۱۲ مگابایت روی RX قابل‌حساب‌کاری ایران می‌نشیند:

* ~۷٫۵٪ سربار سیم tinc (رمزنگاری + padding + ترنسمیشن مجدد زیر ۰٫۵٪ loss)
* ~۳٫۹٪ ACK/درخواست‌های کلاینت که روی همان NIC فیزیکی می‌آیند (در واقعیت هم قابل‌حساب‌کاری‌اند)
* بقیه: ترافیک کنترل ماتریکس

مسیرهای کاهش (برای جلسهٔ توسعهٔ Matrix Agent): tune کردن PTMU/MTU برای کم‌کردن padding، آزمایش Cipher سبک‌تر، و بررسی فشرده‌سازی قبل از تونل. تا رسیدن به ≤ ۱٫۱۰، استقرار با چشم‌پوشی آگاهانهٔ مالک یا بهینه‌سازی انجام شود.

**درگاه استقرار:** AC1 تا AC6 و AC9 و AC10 ✅. AC7 دانلود ⚠️ نیازمند تصمیم مالک یا بهینه‌سازی. AC8 مستند؛ ادعای مقاومت DPI ممنوع تا تست شبکهٔ واقعی توسط مالک انجام شود.

## ۱۱. محدودیت‌ها و صداقت

* نتایج lab روی WSL2/veth است؛ اعداد مطلق (مثلاً CPU) روی سرور واقعی متفاوت خواهند بود — **نسبت‌ها** (تقویت، سربار) و روندها معتبرند.
* tinc 1.0 خط دست‌دادن plaintext می‌فرستد؛ این یک واقعیت قابل‌اندازه‌گیری است که باید قبل از استقرار با مالک در میان گذاشته شود (برچسب: شناسایی‌پذیر در برابر پروب فعال ساده).
* lab هیچ تونل دیگری را پیاده‌سازی نمی‌کند؛ `calibration` فقط فوروارد ساده برای صحه‌گذاری روش است.
